# 设计讨论记录 · 2026-09-29：TerraBlind 与 JEV 的控制边界

本文件是本轮讨论的完整设计记录。结论以 `docs/00-overview.md`、`docs/01-reflex-arc.md`、`docs/03-implementation.md` 与 `docs/05-decisions.md` 为准；本文保留问题、证据、推理和未决项。

## 讨论起点

项目目标是让 Minecraft Agent 在慢模型进行长期规划和决策时，仍能持续对游戏世界做出有意义的局部响应。初始设想是：

- 慢模型维护和编排反射弧；
- 快模型 Jev 在运行时进行快速判断；
- 代码动作库负责具体执行；
- 判断结果和执行结果反馈给前后台模型，形成持续优化闭环。

随后明确了一个限制：Jev 是高级分支选择器，只能处理类型化的客观判断、选择题和判断题，不能可靠地完成开放式填空，也不能直接产出“瞄准哪里”“走到哪个坐标”“按键多久”等连续控制参数。

因此需要回答：**TerraBlind 是如何让 Jev 控制角色的？**

## 预先澄清的概念前提

这次讨论确认，项目中的“可行”不能混成一个判断：

1. **可实现**：组件能否连起来；
2. **可运行**：真实 Minecraft 中能否持续行动；
3. **有效果**：是否比纯规则或纯慢模型更好；
4. **可学习**：弧和动作能否根据反馈逐步改善。

现有文档和代码在本轮之前主要是设计表达，不能当作真实 Minecraft 运行证据。首个总目标仍是 C：完成一个由长期目标驱动的 Minecraft 生存闭环。A（慢模型等待期间仍能行动）是运行时基础，B（根据轨迹与结果优化弧）需要跨多次执行才能证明。

## 可行性判断前的假设与信息缺口

在正式判断前，先列出了设计隐含的前提：

- 快模型能在有限状态投影上稳定做局部判断；
- 游戏能提供足够及时、准确、可复用的状态变量；
- 动作能够被拆成有开始、结束、失败和中断条件的执行单元；
- 慢模型维护弧的收益大于引入的复杂度；
- 局部错误可以被限制，不会长时间持续造成不可逆损失；
- 状态采样、模型判断和动作执行之间能够处理延迟、过期和连接换代；
- Minecraft 的长期目标能够分解为可由局部弧承接的阶段；
- 模型生成的动作工件能够被限制、验证和回退。

会显著改变判断的信息包括：第一个具体任务、真实模型延迟及尾延迟、状态变量的完整性、动作接口是否允许任意代码、失败代价、可重复的回放与基线，以及“可行”究竟指能运行、能提升成功率还是能自动扩展行为。

本轮归纳的常见错误是把“模块关系讲得通”误认为“闭环已经可行”。真正必须测量的是状态是否足够、延迟是否低于动作窗口、动作完成是否可判定、错误是否可限制，以及系统是否优于固定脚本或规则基线。

## 目标选择与验证策略

用户选择 C 作为最直观的总判据：前台大模型维护长期目标，反射弧在局部行动中提供连续性，前台轨迹和长期目标影响后台弧的侧重，动作结果同时反馈给前台和后台。

因此“先接入 Minecraft、用真实场景数据修正设计”被确定为下一步方向。但一次运行只能证明链路是否打通，不能证明弧可复用或后台优化有效：

- A 可以在首轮观察，重点看等待模型时是否停顿、过期回退是否安全、局部动作是否有意义；
- B 必须跨多次有版本的执行，比较弧更新前后的成功率、失败类型和目标推进；
- C 必须包含前台目标、局部弧判断、具体动作执行、结果反馈和下一阶段规划，不能只让固定脚本跑完整个流程。

首个垂直切片应尽量小，但保留这条完整链路，而不是首轮直接声称完成“全 Minecraft 生存”。

## TerraBlind 的实际做法

本轮只读检查了本地 `D:/Codespace/YesWeAreBot/.tmp/TerraBlind`，没有运行它。关键证据来自：

- `README.md`：Jev 约每 300 ms 返回一次类型化判断，代码反射层每帧翻译成按键；
- `Jev/Fight/Dodge.cs`：走位意图、异步请求、TTL、每帧落地；
- `Jev/Fight/Combat.cs`：目标选择、武器选择、提前量瞄准和持续攻击；
- `Jev/Fight/JevCombat.cs`：是否战斗、逃跑、封墙、回血和是否中断放置；
- `Jev/Fight/BossBook.cs`：人工编写的 Boss 战斗知识；
- `Core/ActExecutor.cs`：代码动作、逐帧控制、完成条件、无进展和超时现场。

### 1. Jev 只输出语义意图

Boss 走位的主要问题被拆成两个正交选择轴：

```text
horizontal = Away / Hold / Near
vertical   = Rise / Level / Drop
```

此外还有若干 `noul`：

```text
should_jump_now
should_dash_now
should_grapple_now
```

Jev 不输出方向键，不输出坐标，也不输出钩爪落点。它表达的是“要达成什么”，不是“具体怎么按”。

### 2. 代码选择目标和执行手段

`Combat.Tick()` 由代码完成：

- 选择当前应攻击的 Boss、部件或小怪；
- 选择武器槽位；
- 根据目标位置、速度和武器速度计算提前量；
- 每帧设置光标位置；
- 在攻击动画允许时按下使用键。

Jev 不负责填写 `entityId`、像素坐标或瞄准角度。

### 3. 代码把意图翻译成每帧控制

`Dodge.Drive()` 每帧重新读取游戏状态，并结合 Jev 的意图计算：

- Boss 在玩家哪一侧；
- 哪一侧压力更大；
- 当前距离是否低于或高于目标距离；
- 哪个方向会穿过 Boss 或弹幕；
- 墙、天花板和地面是否允许移动；
- 是否需要跳跃、二段跳、翅膀、钩爪或冲刺；
- 钩爪应搜索哪一个可勾住的方块；
- 具体应写入哪些按键字段。

例如 Jev 选择 `Away + Rise`，代码可能根据当前几何状态执行“向左跑、起跳、必要时冲刺或找钩爪锚点”。同一个意图在不同帧可以落成不同的具体按键。

### 4. 状态先由代码压缩成可判断事实

发给 Jev 的不是原始坐标和全部游戏内存，而是代码计算后的事实，例如：

- 玩家和 Boss 血量百分比；
- Boss 速度与最近一秒峰值；
- 距离及距离偏差；
- 预计多少帧后碰撞；
- 上下左右的空间；
- 当前输出是否下降；
- 弹幕预计命中时间与方向压力；
- 二段跳是否可用。

`BossBook.cs` 还提供人工编写的战斗知识。Jev 的判断因此依赖“派生事实 + 战斗知识 + 有限选项”，不依赖开放式主体意识。

### 5. 等待 Jev 时继续行动

Jev 请求在后台发送，游戏主线程使用上一条意图。意图超过 TTL 后回退到保守行为。代码仍以帧级频率处理移动、瞄准、跳跃、钩爪、冲刺和碰撞修正。

这条链路是：

```text
Jev：几百毫秒更新语义意图
代码：每帧执行、修正和过期回退
游戏：产生真实反馈
```

### 6. TerraBlind 没有实现的部分

TerraBlind 的 BossBook 是人手写的，动作实现和低层反射也是代码。仓库没有证明后台模型能够自动生成、验证并部署新的反射弧；它证明的是“有限语义判断可以驱动复杂的代码执行层”。

此外，TerraBlind 的完整主线主要是手工编排的代码流程。README 明确写了当前里程碑依赖关闭刷怪、无敌等 DragonLens 能力，不能把它直接当成已证明的通用自主生存系统。

## 对 sekizui 的设计启发

### 一、核心模型不推翻，但 JEV 的职责必须收窄

Jev 负责：

```text
approach / hold / retreat
rise / level / drop
fight / flee / ignore
jump_now / dash_now
danger / urgency
```

Jev 不负责：

```text
坐标、像素、实体任意 ID、路径、按键方向、按键时序、开放式参数填空
```

`choice`、`noul`、`score` 仍然是适合的判断类型，但输出应被理解为语义意图，而非完整动作调用。

### 二、显式补出“意图落地”这一层

更准确的运行时结构是：

```text
前台慢模型：长期目标、阶段、完成条件、约束
        ↓
反射弧：状态投影、当前目标上下文、Jev 语义判断
        ↓
意图落地器：目标解析、参数求值、几何计算、手段选择
        ↓
传出原语：移动、跳跃、挖掘、攻击、瞄准、时序
        ↓
完成判据与现场反馈
```

这不是必须新增一个包；第一版可把意图落地器放在动作库或动作执行器内部。但这个职责必须在契约中存在，不能让“Jev 选择动作”隐含承担它。

### 三、模型可见动作与代码原语分层

模型可见的动作应优先是语义行为：

```text
engage_nearest_threat
retreat_from_threat
hold_safe_distance
move_toward_goal
take_cover
```

代码内部仍可使用：

```text
walk(to)
jump()
dig(at)
attack(entityId)
```

默认规则：

1. 代码能确定的目标和参数，代码直接确定；
2. 有限候选中的语义取舍，才交给 Jev；
3. 开放式目标和长期目的，交给前台慢模型；
4. 不让 Jev 任意填写连续参数。

### 四、前台慢模型输出目标契约，而不是逐帧动作

前台应维护：

```text
长期目标
当前阶段
完成条件
约束与优先级
```

反射弧需要在必要时看到这个目标上下文，否则 Jev 只能做脱离任务的通用威胁判断。

例如前台给出“获得铁镐并回到临时基地”，当前弧再判断附近威胁下应战斗、撤退还是继续采集。弧不需要知道完整计划，但需要知道当前局部行为服务于哪个阶段。

### 五、A、B、C 的验证边界

- **A**：验证慢模型请求期间，代码落地器和传出原语仍持续行动；重点看停顿、过期回退、局部纠偏和中断。
- **B**：初期只优化弧、问题、criteria、状态投影、候选语义动作和回退行为；不让后台直接改瞄准、寻路、跳跃物理、按键时序或保命阈值。
- **C**：验收必须覆盖“前台目标 → 弧判断 → 意图落地 → 原语执行 → 结果反馈 → 前台继续规划”的完整链路。仅仅跑通固定代码流程不算 C。

## 本轮形成的工作约束

以下是进入实现前的设计约束，仍需真实 Minecraft 垂直切片验证：

1. Jev 的输出是语义判断，不是连续控制参数。
2. 目标解析、参数求值、几何计算和执行时序由代码负责。
3. 模型可见动作优先是语义动作，底层原语只作为动作实现。
4. 前台慢模型维护目标、阶段和完成条件；反射弧消费压缩后的目标上下文。
5. 后台优化初期修改弧和判据，不直接修改低层传出代码。
6. 真实 Minecraft 运行是下一步主要证据来源；文档和纸面推理不能替代它。
